# 迭代 5A 复盘：评测结果可信基线

## 一、迭代目标

5A 不增加新的业务能力，只解决评测结果可能被误判的问题：

> 失败不能被包装成通过。

同时建立最小的自动化测试基线，确保这几条规则以后不会被改坏。

## 二、实际完成内容

### 1. 修正评测结论

- Agent 报错时，评测不能通过。
- Agent 没有完成运行时，评测不能通过。
- Agent 返回空内容时，评测不能通过。
- 空断言不再自动得到满分，而是标记为 `skipped`。
- LLM Judge 不可用或调用异常时，不再偷偷降级成规则 Judge 并正式判定通过。
- 用户明确选择 `rule-based-*` 时，仍然可以使用规则 Judge 正式判定。

### 2. 区分两类状态

结果现在区分：

- **运行状态**：程序是否正常执行完成；
- **评测结论**：Agent 的结果是否通过评测。

因此可以区分“Agent 做错了”和“评测平台本身出错”，不再只看一个模糊的 `status`。

### 3. 补充必要的清理

- 正常运行和异常运行路径都会尝试关闭 Executor session。
- MCP adapter 关闭时清理内部注册状态。
- CLI 批量校验/运行 Scenario 时，每个 Scenario 使用独立的 Runner，减少状态串扰。
- 数据库 Fixture 的 metadata 不再保存完整数据库连接 URL。

### 4. 增加最小测试基线

新增 18 个测试，覆盖：

- 空断言语义；
- Agent 失败、缺少结果、断言失败等 verdict 规则；
- Judge disabled、显式 Rule Judge、LLM Judge 不可用；
- 顶层状态与致命错误；
- secret 脱敏；
- 路径越界；
- 旧版 `AssertionResult` 默认值兼容。

## 三、验证结果

| 检查项 | 结果 |
|---|---|
| 测试依赖安装 | 通过，使用清华镜像 |
| 全量 pytest | 18 passed |
| 8 个 Scenario 配置校验 | 全部通过 |
| 修改后的 Python 文件编译 | 通过 |
| `git diff --check` | 通过 |

本轮没有执行真实 Scenario run，避免覆盖现有报告文件。

## 四、范围纠偏

实施初期范围曾经扩大到报告系统、安全体系、Task/SSE、全局 timeout 和完整资源治理，超出了 5A 的合理边界。

复盘后已收敛：

### 保留在 5A

- 评测通过语义；
- 空断言和 Judge 异常语义；
- 最小运行隔离与 session 清理；
- 最小测试基线。

### 明确延期

- `reports/runs/<run_id>` 完整报告迁移；
- 失败运行的统一归档和原子产物发布；
- 全链路脱敏和完整路径安全治理；
- Task/SSE 持久化、恢复、取消和 retention；
- 全局协作式 timeout；
- MCP 全面服务化与 DB 数据面改造。

这些内容不是 5A 的遗漏，而是后续独立迭代，避免继续扩大本轮范围。

## 五、做得不好的地方

1. **一开始把规划文档中的多个后续主题同时当成 5A 任务执行，导致改动面过大。**
2. **在测试尚未运行前就修改了较多核心模块，验证顺序不够靠前。**
3. **部分初始改动没有充分考虑现有 API 和报告目录的兼容性，后来主动回退了报告路径迁移。**
4. **任务清单未及时更新，实际验证完成后仍显示为未完成。**

## 六、结论

5A 已达到收尾条件：

- 核心误判路径已被拦住；
- Judge 的意外不可用不会伪造正式通过；
- 空断言不会伪造满分；
- 最小回归测试全部通过；
- 存量 Scenario 配置全部通过校验。

下一步不应继续向 5A 添加功能。后续若进入 5B，应先单独冻结 MCP/DB 数据控制协议，再做 MCP 服务化和数据面改造。
