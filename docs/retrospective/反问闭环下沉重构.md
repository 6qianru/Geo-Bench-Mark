# 重构复盘：反问闭环下沉（ActorRuntime/AgentRuntime → UserSimulator）

> 日期：2026-08-24 · 状态：**已完成并回归验证**
> 性质：架构重构（非功能迭代），发生在迭代 3（模拟用户 actor 自动多轮）与迭代 4（云端 MCP）之间，未单独立项
> 关联：`迭代3-模拟用户actor自动多轮.md`（被重构的前身）、`../design/00-系统总体设计.md` §9.5/§9.6（现状）

## 1. 为什么重构

迭代 3 的实现把"agent 反问 → 模拟用户回答"的循环放在 **runner 层**：`ActorRuntime.reply()` 生成回答，runner 的 while 循环把回答回填为下一轮消息。跑通后发现三个结构性问题：

1. **runner 必须理解每个 executor 的对话协议**。runner 层循环假设所有被测对象都遵守 `need_interaction=True/finished=False` 的信号——这只对本地 skill agent 成立。orchestrator 的多轮是它自己指挥外部 agent；external_driven 的多轮是外部 agent 主导；HTTP 黑盒根本没有中途交互态。一个全局 runner 循环硬套四种会话模型，信号语义开始漂移（external_driven 被迫恒返 `need_interaction=False` 来绕开 runner 循环）。
2. **模拟用户的回答时机不受会话上下文控制**。ActorRuntime 只拿到 conversation 文本，不知道当前 executor 处于什么阶段（orchestrator 第几条指令、skill 是否已解析出数据集），回答质量受限。
3. **每加一种新 executor 都要在 runner 里再写一遍交互分支**，扩展成本线性增长。

**方向**：反问闭环是"某一种会话内部的事"，不是"评测主流程的事"。下沉到 executor 内部，runner 退回纯编排。

## 2. 改动全景

| 层 | 删除 | 新增 |
|---|---|---|
| runtime | `actor_runtime.py`、`agent_runtime.py` 整体删除 | `user_simulator.py`（共享 UserSimulator） |
| runner | actor 循环、`scenario.actor` 配置读取 | `_user_config()` 把 `agent.user_*` 扁平注入 `role_model_config["user"]`；接受 executor 返回的完整 conversation |
| models/scenario.py | `ActorConfig` 块、`runtime.actor_model` 字段 | `AgentConfig.user_enabled/user_profile/user_goal/user_max_turns/user_model` 扁平字段 |
| executors | — | skill/orchestrator/heuristic/external_driven 四个 executor 各自在 session 内闭环反问 |
| models/result.py | — | `ExecutorStepResult.conversation`：executor 内部跑完多轮后返回完整会话记录 |

### UserSimulator 设计要点

- **规则 or LLM 双实现**：`user_model` 为空或 `rule-based-*` 前缀 → 规则回答（正则从 `user_goal` 提取数据集/距离/格式 + 动态候选选择）；否则 LLM persona（temperature 0.7 保自然度），LLM 失败自动降级规则——保证反问永远有回答、评测不卡死。
- **动态候选选择优先于关键词匹配**：agent 探索后列出的选项（如"可选数据集：schools_a、schools_b、rivers"）用 goal 目标词做精确 > 子串 > 取第一个匹配，覆盖"agent 搜索数据集后让用户确认"场景。
- **askback.py 单一事实源**："外部回复是反问/完成/进展"的判定收敛在独立模块，executor 分类与 judge 规则镜像共用，避免两处判定漂移。
- **conversation 随 ExecutorStepResult 返回**：报告的完整对话由 executor 给出（含模拟用户回答），runner 不再自拼；空列表时老 executor 兼容走自拼路径。

### 各 executor 的闭环形态

| executor | 闭环方式 |
|---|---|
| `skill` | agent 输出 `[NEED_INTERACTION]` → UserSimulator 回答追加进 messages → 再 invoke，直到 `[FINAL]`/无前缀/`user_max_turns` 耗尽 |
| `heuristic` | 缺数据集/距离时直接调 `UserSimulator.reply()` 解析填入 resolved_*，不再返回 need_interaction |
| `orchestrator` | react 流程内 agent 输出 `[NEED_INTERACTION]` → 回答累积进 react_messages（跨轮不丢上下文）→ 继续；仅 react 流程且 `ask_user: true` 生效 |
| `external_driven` | 外部回复经 askback 分类：ask → 模拟用户回答；continue → 引导一句；complete/max_turns → 终止 |

## 3. 配置迁移（破坏性变更，存量场景已同步迁移）

```yaml
# 旧（已失效——pydantic 会静默忽略未知块 actor:，等于没配！）
runtime:
  actor_model: deepseek-v4-flash
actor:
  enabled: true
  max_turns: 3
  goal: 使用 schools 数据对学校周边 500 米做缓冲区分析

# 新
agent:
  ask_user: true            # orchestrator 场景：agent 会不会反问
  user_enabled: true        # 反问时模拟用户是否自动回答
  user_profile: normal_user
  user_max_turns: 3
  user_goal: 使用 schools 数据对学校周边 500 米做缓冲区分析
  user_model: rule-based-user   # 空/rule-based-* → 规则回答
```

**注意旧配置的静默失效**：pydantic 默认忽略未知字段，存量场景若残留 `actor:` 块不会报错，但模拟用户设定全部丢失（回落默认值）。本轮已迁移仓内全部场景（`buffer_school_500m_001.yml` 等）；外部自建场景需手动检查。

## 5. 已知风险与未验证项

- **LLM 模拟用户质量未系统评估**：真机主要用规则回答（`rule-based-user`）；persona 模式（真实 LLM 当用户）的回答自然度、是否会引入噪声，待真机专项评估。
- **harness 方差叠加**：模拟用户若用 LLM 实现，其回答方差会叠加进 orchestrator 本就存在的 harness 方差（见记忆 `orchestrator-freeform-variance`）。量化时要把两者一起测。

## 6. 过程经验与教训

- **循环归属跟着会话归属走**：谁拥有会话状态，谁就该拥有循环。runner 是流程编排者，不该理解任何一种被测对象的对话协议。判断标准很朴素——如果某个信号字段（need_interaction）在某个 executor 里永远返回同一个值来"绕开"框架行为，说明框架抽象和现实已经错位。
- **破坏性配置变更要主动清残留**：pydantic 静默忽略未知块意味着旧配置"看起来还能跑"，实际模拟用户已丢。这类坑比报错更危险——发现即全量迁移并在设计文档标注新旧对照。
- **先有单一事实源，再做镜像消费**：askback 分类先抽成独立模块，judge 规则镜像才敢直接复用。顺序反过来（两处各写一份再对齐）必然漂移。
